# AstraWealth: changes, 25 September 2026

Made against the growth plan for AstraWealth (the seasonal-sprint product).
Read the first section before you deploy — one change needs an environment
variable that does not exist yet, and the site will not sign anyone in without
it.

---

## Do this before you deploy

**Set `AW_SESSION_SECRET` in the Vercel project, in all three environments.**

Generate one:

```
node -e "console.log(require('crypto').randomBytes(32).toString('hex'))"
```

Then Vercel → the AstraWealth project → Settings → Environment Variables →
add `AW_SESSION_SECRET`, paste, tick Production, Preview and Development, save,
and redeploy.

Without it, `/welcome` returns "Sign-in is temporarily unavailable" and nobody
reaches the dashboard. That is deliberate: the alternative is a paywall that
opens when the configuration is wrong, which is what the old code did.

Everyone signed in today is signed out by this change and has to enter their
email again once. There are few enough of them that this does not matter now,
and it will matter later.

**Optional, same screen:** set `NEXT_PUBLIC_SITE_URL` to the site's real
address (`https://...`, no trailing slash). It only affects link previews.

## 1. The paid tier was open to anyone

This is the one worth reading.

**What was happening.** `/api/verify-membership` checked the email against Whop
properly, then set a cookie whose entire value was that email in plain text.
`/dashboard` let a visitor in if a cookie called `aw_session` existed and was
not empty:

```ts
const session = cookieStore.get("aw_session");
if (!session || !session.value) redirect("/welcome");
```

`httpOnly` stops page scripts reading a cookie. It does not stop a person
typing one. Anyone could open devtools, add `aw_session=x`, reload, and be
inside the Founder tier.

Separately, the three endpoints behind that tier — `/api/consultant`,
`/api/daily-intelligence`, `/api/monthly-report` — checked no session at all.
Each spends a Gemini call per request. They could be driven from curl by
anyone who knew the paths, on your bill, with no membership involved.

**What I changed.**

- New `lib/session.ts`. The cookie now carries
  `base64url(email).expiry.HMAC-SHA256(...)`, signed with `AW_SESSION_SECRET`
  and compared with `timingSafeEqual`. A cookie the server did not issue is
  rejected, and one older than 24 hours expires — the same 24 hours the old
  `maxAge` already used.
- New `lib/requireMember.ts`. Two lines at the top of each paid route:

  ```ts
  const denied = requireMember(req);
  if (denied) return denied;
  ```

  Unauthenticated callers get a 401 before any model call is made.
- `app/dashboard/page.tsx` verifies the signature instead of checking that the
  cookie is non-empty.
- `app/api/verify-membership/route.ts` issues the signed token, and returns 503
  rather than a broken session if the secret is missing.
- The cookie's `secure` flag is now `process.env.NODE_ENV === "production"`.
  It was hardcoded `true`, which means the cookie was silently dropped on
  `http://localhost` and sign-in could not be tested locally.

**What I did not change, and you should consider.** Membership is checked once,
at sign-in, and the token is then good for 24 hours. If someone cancels, they
keep access until it expires. That is a reasonable trade for now; re-verifying
against Whop on each dashboard load is the stricter version if you ever want it.

**Also worth knowing:** `DEMO_ACCESS_EMAILS` in `lib/verifyMembership.ts` grants
full access to any address listed in it. That is fine as a demo hatch, as long
as you remember it is there.

## 2. A failed model call no longer shows an apology

**What was happening.** `/api/reading` returned a 502 whenever Gemini failed or
`GEMINI_API_KEY` was missing, and the free reveal screen said "your reading is
taking longer than usual". That message appears at the exact moment the product
has to be most convincing — it is the screen the paywall sits under.

**What I changed.**

- New `lib/fallbackReading.ts`: twelve handwritten Life Path readings and twelve
  observations about how a business name reads, composed into a four-sentence
  reading. Dry, specific, and written so that a visitor who receives one has no
  idea anything failed.
- `/api/reading` now always returns a reading, and reports `source: "model"` or
  `source: "fallback"` in the JSON so you can tell the two apart in logs. A
  missing API key is logged loudly as the deployment problem it is, rather than
  being shown to a visitor as a 500.
- `components/HeroSection.tsx` falls back client-side too, for the case where
  the request never reaches the server at all.

The reading is worth reading on its own. Each Life Path entry names a real
operating edge and the failure mode of that same trait — "you leave at month
nine, right at the point where the boring version of the business starts to
compound" — because a reading that only flatters gets shared once and believed
never.

## 3. A disclaimer, on the reading and on the share card

There was none anywhere in the codebase.

The product charges money and talks about wealth, timing, and when to make
bigger bets. Two lines now say what it is:

- Under the founder reading: *"AstraWealth is a numerology tool for reflection
  and entertainment. It is not financial, investment or business advice, and
  nothing here predicts a result."*
- On the share card, small, at the bottom: *"Numerology, for reflection. Not
  financial advice."*

This is not defensive throat-clearing. The card travels to people who have
never seen the site and has to be honest on its own, and a product that states
its limits plainly is easier to trust on everything else it says.

## 4. The share card

`components/ShareCard.tsx`, rewritten. This image is the growth mechanic for a
product with no ad budget, and it had four problems.

- **It did not say where it came from.** The footer read `astrawealth`, which is
  not an address. It now draws the host the page is actually served from, so it
  is correct today on the Vercel URL and correct the day you attach a domain,
  with no code change.
- **A long business name ran off the card.** There is now a fitting pass that
  shrinks the type, then wraps to two lines, then truncates — in that order.
- **The first download used the wrong fonts.** `draw()` ran before the webfonts
  had loaded, so the canvas fell back to a system face. It now waits for
  `document.fonts.ready`, and the button says "Drawing your chart..." while it
  does.
- **The hierarchy was wrong.** The business name — the thing a founder is
  actually sharing — sat below the number in small grey text. It is now the
  first thing under the wordmark, with the number labelled beneath it.

Also: the download filename is now the business name rather than a constant, so
a person with two charts does not end up with `(1)` in the name.

## 5. Encoding

`lib/numerology.ts` and `app/layout.tsx` had double-encoded em dashes
(`AstraWealth â€" Pythagorean Numerology Engine`), including in the page title,
which meant the mojibake was visible in the browser tab and in every shared
link. Four files also carried UTF-8 BOMs.

Fixed, and the punctuation is now ASCII throughout so it cannot silently come
back the next time a file is opened in an editor that guesses the encoding.

`app/layout.tsx` also gained Open Graph and Twitter card metadata, which a
product designed to be shared should have had from the start.

## What I could not do from here

There is no shell on this machine through the session, so nothing here has been
installed, built, typechecked against your `node_modules`, or committed. Run
`npm run build` before you push — the changes are small and self-contained, but
I have not seen them compile in your project.

`lib/numerologyMeanings.ts` is not imported anywhere. It is either dead code or
something you meant to wire into the Wealth Chart tab. I left it alone rather
than guess.
